# v4 architecture seam (patch against c17141f)

These modules are additive and do not alter the v2 orchestrator or `cviaf/lab` files. They are contracts, not claims that the existing checks already implement the v4 battery or calibrated power curves.

1. Register a `DetectorPlugin` adapter for each existing check in `cviaf/orchestrator.py` and `cviaf/lab/detectors.py`. Its manifest declares taxonomy keys, concrete access and asset requirements, supported formats, cost, battery slice/digest and emission type. Import the adapters into a `Registry` at composition time; core registry does not import detector implementations. Do not register a detector until its null calibration and evidence pointer exist.
2. Translate intake into `Context`: access granted is distinct from actual assets, model black-box and white-box are distinct capabilities, formats are explicit (`ONNX`, `TorchScript`, `COCO`, `YOLO`), and the operator declares threat classes and risk weights. Use `plan(registry.manifests(), context)` before calling checks. Persist `Plan.to_dict()` in the hash-chained audit log (`AuditTrail.append`) and include it in the report.
3. Call `registry.execute(plan.selected, assets, slices_by_id, budget)`. A detector returns `Result('ran', ...)` with finite statistic, one of p/e/floor, calibration digest matching its manifest, actual cost and evidence pointer. A skipped check names the reason and coverage impact. An exception or malformed result becomes an `error`, which has no coverage credit. The engine must not convert an error into a clean result.
4. Generate `coverage_matrix` from the actual results with `generate_coverage`. Supply measured floors and evidence pointers from a reproducible battery run. Without a measured floor, an executed detector is at most **partial**, and absent/error checks are **not covered**. The taxonomy table is a vocabulary and an explicit ceiling for physical, clean-label, and ambiguous drift, not a promise of detection. For no-applicable-check acceptance, policy should remain conservative.
5. Compute `completeness(plan, results)`. Accept is blocked on rejected applicable checks, errors, skipped checks, and declared classes with no planned detector. The aggregate detector count is not a per-finding coverage fraction: calculate each finding's `battery_coverage_fraction` from executed/expected applicable checks for that finding's attack class and cap it at report completeness. Keep v2 `assessments`, `audit_trail`, and `coverage_statement` unchanged for consumers, adding `schema_version: "3.0"`, threat model, battery, plan, completeness, per-finding structured confidence and floors, and coverage matrix. Validate the original v2 report with `cviaf.governance.schema.validate_report` before migrating, then validate the enriched v3 report with `cviaf.schema_v3.validate_report`. The v2 validator expects numeric `finding.confidence`, so it cannot validate the enriched report directly. Keep a v2 projection for legacy consumers rather than sending them v3 confidence objects. JSON Schema source is `cviaf/schema_v3/assurance-report-v3.schema.json`.

The included Python validator checks v3 core types and cross-field safety gates but is not a complete Draft 2020-12 implementation. For complete schema keyword checking, downstream consumers can run any Draft 2020-12 validator against the companion schema. No static assertion of NIST certification or measured detector power follows from a manifest.

Run the independent tests with `python3 -m unittest discover -s tests -p test_v4_architecture.py`; they need Python 3.10+ and no optional ML packages.
