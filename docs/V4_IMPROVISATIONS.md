# V4 live-run changes and limitations

Run on the repository's frozen MVP corpus at c17141f, from a clean clone; no existing `cviaf/lab` files or user working files changed.

1. First attempt to run `python3 -m cviaf.lab assure --corpus runs/mvp --model oga_patch_fixed_s5 --out /tmp/cviaf-v4-baseline --access-level black-box` failed before assessment because scikit-learn was absent in this container. Installed the repo's declared scikit-learn dependency locally for verification, then reran successfully. This is an environment issue, not a patch dependency; the new planner/contracts remain standard-library-only.
2. Built `python3 -m cviaf.v4_assurance --corpus runs/mvp --model oga_patch_fixed_s5 --out /tmp/cviaf-v4-wired --access-level black-box`. It runs the existing v2 engine into `out/legacy`, separately plans and executes two actual native TinyDetector checks (TRACE CTC and FTC), and writes `assurance_report_v3.json`, `coverage_matrix.json`, and a hash-chained `planner_audit_trail.json`. It reconstructs clean held-out `eval_clean` target and separate `cal_clean` null blocks, computes block-level empirical p-values, validates emissions and the final v3 report. It neither uses ground truth for the planned detector nor represents legacy numeric confidence as calibrated: the original findings remain in `legacy_findings`, and the v3 `findings` list is empty until a proper v3 finding can be warranted.
3. The first live run selected and executed both checks, CTC p=0.4375 and FTC p=0.6875. Without measured attack-class power/floors, those cells are **partial**, not covered. Four modeled BadDet cells are partial; the other declared attack cells are not covered or not applicable. This exposed an acceptance flaw in the first bridge: the detector-count completeness gate could report `executed=applicable` while coverage was still partial. The bridge now blocks `accept_permitted` on every declared cell lacking measured coverage as well. The result remains quarantine because the v2 engine flagged its own findings, not because the v4 probes detected the attack.
4. A second run used ODA and a 60-second plan budget. Planner chose CTC (three weighted classes) and explicitly rejected FTC at 75 seconds; the ODA coverage cell was correctly **not_covered**, while completeness showed 1/2 executed and `model.trace.ftc: BUDGET_EXHAUSTED`. The two extra audit entries persist the plan and detector outcomes; the original v2 audit remains unchanged.
5. The report initially pointed detector evidence at the legacy bundle, which contains scoring-only ground truth. Changed the pointer to the legacy report itself, so an analyst following the evidence does not inadvertently see attack truth in the probe record.

The `seconds` manifest cost is an estimate used to select checks, **not** a runtime enforcement mechanism. `cost_actual` times the actual probe; estimated plan costs are not a runtime enforcement boundary. The calibration block p-value's granularity (16 null blocks of eight images, min p=1/17) cannot justify a strong detection claim. Clean held-out probes do not test unknown triggered inputs or bound adaptive attack success. The current bridge is deliberately conservative: it is a real execution path and gap report, not a production AB-1 battery, calibrated v3 finding generator, or live enforcement of every planned detector in the legacy engine. Replacing the legacy v2 execution path with plan-selected plugins remains an engine integration step for other lanes. The existing v2 static coverage statement remains in `legacy`; consumers must use the new v3 matrix for this run's actual coverage.
